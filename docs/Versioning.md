# Versions and API stability

UnderRailWorks has three version numbers. Mods should only ever need to think about the second.

| What | Where | Means |
|---|---|---|
| Works release | `FixVersion.Value` (src/Runtime/Version.cs), the download's name | the product: fixes, loader, everything. Any number of releases can share one API version |
| **API version** | `WorksApi.Major` / `Minor` (src/Runtime/WorksMod.cs), `WorksApi.Version` at run time | what mods can use. A mod's `mod.json` says which it was built for: `"works": "1.2"` |
| Game version | `WorksApi.GameVersion` (running), `WorksApi.MadeForGameVersion` | the UnderRail build Works was made and checked for |

## What is the API

Everything public in the `UnderRailWorks` namespace, and nothing else:

- `UnderRailWorks.Internal` is public only because the patched game calls into it. It changes whenever it needs to.
  A mod that uses it gets a note in the Mods tab ("uses UnderRailWorks internals").
- The game's own types (scrambled names: `c5x`, `bm6`...) are not API, and they change with every game update. Works
  wraps what mods need; a gap is filled in Works, not worked around in mods (UnderRailWorks.md, "Mods use only Works").
  Mods that reference the game or use Harmony anyway get a note ("may break with a game update").
- `object`-typed keys (`Layer.Key`, `WorldView.Key`...) are opaque: compare them, don't look inside.

The API as of the last release is listed in `api/UnderRailWorks.api.txt` (one line per type and member, generated by
`tools/apicheck/ApiSurface.cs`). It never contains a game type: the build fails if one shows through.

## The rules

Semantic versioning, applied to the API:

- **Minor** (1.2 -> 1.3): something was added. Every mod built for 1.0-1.2 keeps working.
- **Major** (1.x -> 2.0): something mods could use was removed or its signature changed. Mods built for 1.x are
  refused with a message until they're rebuilt.
- **0.x** (now: 0.9): a preview. Each minor may break; mods must match the minor exactly.

A mod built for `"works": "1.2"` loads on any 1.x from 1.2 up, and is refused on 1.0-1.1 (too old) and on 2.0
(a break). Before loading, Works also checks every type and member the mod's DLL uses from Works (`ModCheck`); if one
is missing (a mod built for a newer Works than its `mod.json` says), it isn't loaded, and the Mods tab names what's
missing. The game never crashes later on a missing method.

## How the build enforces it

`build.sh` compares the API it just built with `api/UnderRailWorks.api.txt`:

- removed or changed lines without a new major (a new minor while 0.x): **the build fails**, listing them;
- added lines without a new minor: a warning (`release.sh` makes it an error);
- a game type in the API: the build fails.

`release.sh` builds with that check strict, and after the release writes the new API into
`api/UnderRailWorks.api.txt`, committed with the release.

## Changing the API without breaking mods

- **Add** instead of change: a new overload, a new optional event, a new property.
- **Retire** a member by marking it `[Obsolete("use X")]` and keeping it working until the next major version.
- **Never** change a public signature in place, turn a field into a property (or back), make a public type sealed or
  abstract, change an enum's values, or change a `const` (mods compile constants into themselves).
- Default parameter values are compiled into mods too: changing one only reaches mods when they're rebuilt.
- New events and hooks: handlers run inside Works' error handling (a handler that throws is reported, and after 10
  failures removed), so adding one is always safe.

## A mod's own versions and its save data

A mod's own version (`"version"` in mod.json) is the player-facing one; other mods depend on it with
`"requires": ["Other@1.2"]`. Its save data outlives it: a save made with version 1 of a mod is loaded by version 2.
The save records which version of each mod wrote its data (`SaveData.WrittenBy`; null for data from before Works
recorded it), so a mod can migrate an older layout when a save loads. Data of a mod that isn't installed is kept in
the save untouched, with the version that wrote it.

## Game updates

Works reaches the game through readable wrappers tied to one game build (`MadeForGameVersion`). After a game update:

1. At start, Works checks every game member it looks up (GameNames) and installs its hook groups one by one; a group
   that fails leaves the rest working.
2. If anything didn't fit, the player is told once on the main menu which parts, and that mods using them may not
   work (WorksHealth). Mods can read `WorksApi.Unavailable` and say so themselves.
3. For the fix: `tools/names/Remap.cs` maps the old names to the new build's; update Works, check it on the new game,
   then set `FixVersion.ForGame` (release.sh refuses a release whose game version doesn't match it).

Mods built only on the API need nothing: the same mod DLL keeps working on the updated Works.

## Testing aids

- `WORKS_FAIL_GROUP=<group name>` (environment): that hook group fails at start, as after a game update.
- `tools/testmods/HalfBroken`: fails in Load after registering things; nothing it registered may stay.
- `tools/testmods/NeedsNewer`: built against a stand-in for a newer Works; must be refused by name.
