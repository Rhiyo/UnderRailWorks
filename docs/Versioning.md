# Versions and API stability

UnderRailWorks has three version numbers. Mods should only ever need to think about the second.

| What | Where | Means |
|---|---|---|
| Works release | `FixVersion.Value` (src/Runtime/Version.cs), the download's name | the product: fixes, loader, everything. Any number of releases can share one API version |
| **API version** | `WorksApi.Major` / `Minor` (src/Runtime/WorksMod.cs), `WorksApi.Version` at run time | what mods can use. A mod's `mod.json` says which it was built for: `"works": "1.2"` |
| Game version | `WorksApi.GameVersion` (running), `WorksApi.MadeForGameVersion` | the UnderRail build Works was made and checked for |

Why one API version and not one per area (drawing, UI, combat...): Works is one DLL in one download, so only one
combination of areas ever exists, and the areas share types (a drawing handler gets a Character, Co-op uses the
hooks and SaveData). SMAPI, tModLoader, BepInEx and Forge do the same. Areas still mature at their own pace through
`[Preview]`: a preview area may change in any release and becomes stable by dropping the attribute, in a minor
release. Mods that offer APIs to other mods version those themselves (their own `"version"`, `"OtherMod >= 1.2"`).

## What is the API

Everything public in the `UnderRailWorks` namespace, and nothing else:

- `UnderRailWorks.Internal` is public only because the patched game calls into it. It changes whenever it needs to.
  A mod that uses it gets a note in the Mods screen ("uses UnderRailWorks internals").
- The game's own types (scrambled names: `c5x`, `bm6`...) are not API, and they change with every game update. Works
  wraps what mods need; a gap is filled in Works, not worked around in mods (UnderRailWorks.md, "Mods use only Works").
  Mods that reference the game or use Harmony anyway get a note ("may break with a game update").
- Members and types marked `[Preview]` (co-op's plumbing, ability ids, the AI's target, a few new ones) aren't covered
  by the API version yet: they may change in any release, they aren't in `api/UnderRailWorks.api.txt`, and mods using
  them get a note. They become stable by dropping the attribute, which is an addition (a new minor). A stable member
  may not use a preview type (the build checks).
- The API uses only .NET's, FNA's (XNA's) and Works' own types: the build fails on any other (a third party's type,
  e.g. Harmony's, would freeze its version into the API).
- `object`-typed keys (`Layer.Key`, `WorldView.Key`...) are opaque: compare them, don't look inside.
- The world-drawing surface (WorldDraw, Outlines, Layer, LayerSet, MapObject, WorldView, DrawContext, GameBatch,
  LayerShader, Interface) is stable since Nov 2026, for Occluded Characters (Wall Vision) as one of the first
  mods. Guarantees: with no handlers every drawing point does what the stock game does; a drawing handler that throws
  switches off all of that mod's drawing handlers and outline requests for the session (the game's drawing state may
  be half changed), the game carries on; outline requests belong to a mod (forgotten on reload, errors reported).
  Tested by `tools/smoketest/drawing.sh` (every member of every handle on every layer for 120+ frames, layers and tile
  extras drawn by a handler, each Occluded Characters effect, a handler failing on purpose; at 1080p and at 4K with
  the interface at 200%).

The API as of the last release is listed in `api/UnderRailWorks.api.txt` (one line per type and member, generated by
`tools/apicheck/ApiSurface.cs`). It never contains a game type: the build fails if one shows through.

## The rules

Semantic versioning, applied to the API:

- **Minor** (1.2 -> 1.3): something was added. Every mod built for 1.0-1.2 keeps working.
- **Major** (1.x -> 2.0): something mods could use was removed or its signature changed.
- **0.x** (now: 0.9): a preview; any minor may remove or change things.

**What decides whether a mod loads is what it uses, not the number** (as SMAPI, unlike tModLoader). Before a mod's
code loads, Works checks it against the installed UnderRailWorks.dll (`ModCheck`, metadata only, nothing runs):

- every Works type and member it uses exists, with the same signature, and is still public;
- every override in its classes still overrides a Works method (else it would silently never be called);
- every abstract member of a Works class it derives from, and every member of a Works interface it implements, is
  implemented (else it would fail to load).

If all of that holds, the mod loads, whatever `"works"` version its `mod.json` declares: a mod built for 1.4 runs on
2.0 when 2.0 didn't touch what it uses, and on 1.2 when it uses nothing added after 1.2. A major version then only
stops the mods that use what it changed. When something is missing, the mod isn't loaded and the Mods screen names
what (up to five), so the player knows it needs an update; the game never crashes later on a missing method.

The declared version is information: the Mods screen shows it ("Built for UnderRailWorks API 1.4"), and the log notes a
difference. Players get no warning for it: a mod that passed the check works, and a warning they can't act on would
only teach them to ignore warnings. Notes that do appear on a mod (grey, in its details): it uses retired API
(`[Obsolete]`, still working, removed at the next major), preview API, Works' internals, the game's own code or Harmony.

What the check can't see: a member that kept its signature but changed what it does. That's why the rule below is
"add instead of change".

## When it's locked: at GitHub releases only

Between releases nothing is locked and no version number changes: development is free to change anything.

- `api/UnderRailWorks.api.txt` is the API **of the last GitHub release**, written by `release.sh` when it releases.
  Until the first release there is none, and nothing is locked.
- `build.sh` reports how the API changed since that release (a line per change); it never fails a build for it.
- `release.sh` refuses to release when the changes aren't covered by `WorksApi`'s version (a removal or change needs
  a new major, a new minor while 0.x; an addition a new minor), or when a game or third-party type is in the API.
- Version numbers (Works' `FixVersion`, `WorksApi`, each mod's `"version"`) go up only for a release. Between
  releases, changes are tracked in git. Where builds must recognise each other (Co-op's host and joiners), a separate
  protocol number goes up with each incompatible change (`Coop.Protocol`); the handshake compares version and protocol.

## Changing the API without breaking mods

- **Add** instead of change: a new overload, a new optional event, a new property.
- **Retire** a member by marking it `[Obsolete("use X")]` and keeping it working until the next major version (mods
  using it get a note, so their authors hear before it goes).
- **Never** change a public signature in place, turn a field into a property (or back), make a public type sealed or
  abstract, change an enum's values, or change a `const` (mods compile constants into themselves).
- Default parameter values are compiled into mods too: changing one only reaches mods when they're rebuilt.
- New events and hooks: handlers run inside Works' error handling (a handler that throws is reported, and after 10
  failures removed), so adding one is always safe.

## A mod's own versions and its save data

A mod's own version (`"version"` in mod.json) is the player-facing one; other mods depend on it with
`"requires": ["Other >= 1.2"]`. Its save data outlives it: a save made with version 1 of a mod is loaded by version 2.
The save records which version of each mod wrote its data (`SaveData.WrittenBy`; null for data from before Works
recorded it), so a mod can migrate an older layout when a save loads. Data of a mod that isn't installed is kept in
the save untouched, with the version that wrote it.

## Behaviour: what the signature check can't see

A member can keep its signature and change what it does, on purpose or by accident. No framework catches that
mechanically; in every one (SMAPI's migration pages, tModLoader's porting notes and month-long preview branch,
Forge's changelogs) the mod's author updates the mod. Works keeps such changes rare, makes them visible early, and
limits the damage:

- **Don't change, add.** A behaviour that must change becomes a new member or an option; the old one keeps its
  behaviour, marked `[Obsolete]` until the next major version.
- **Tests on results, not just signatures.** smoke.sh and drawing.sh check what the API does (damage dealt, what an
  event passes, what a save holds, every drawing handle's members). `build/api-coverage.txt` (tools/apicheck/ApiUse.cs,
  every build) lists the stable members the test mods exercise, those only shipped mods use (they run, nothing checks
  the result) and those nothing uses: at Nov 18 2026, 487 / 289 / 321 of 1,097. A stable member without a test can
  change unnoticed, so **release.sh refuses a release that adds a stable member without one** (against
  `api/UnderRailWorks.untested.txt`, written at each release): test it, or mark it `[Preview]` until it has one. The
  backlog is worked down over time (TODO.md).
- **Say it.** Every release's notes have a "Behaviour changes:" line for mod authors ("none." when none; release.sh
  refuses notes without it), and the notes carry the API changes since the last release.
- **Early.** A version with a "-" (`1.1.0-preview.1`) is published as a GitHub pre-release: authors can test against
  it before players get it.
- **Contained.** A mod that breaks anyway doesn't take the game down: its failing handler is reported with its name,
  switched off after repeated failures, and the Mods screen shows which mod had errors.
- **If it's ever unavoidable:** the mods' declared `"works"` version allows keeping the old behaviour for mods built
  before the change (as Android's targetSdkVersion), where Works knows which mod is calling (handlers, registrations).
  Not used so far.

Update checks (telling players a newer version of a mod exists, as SMAPI does) wait until there's a settled place
mods are published.

## Game updates

Works reaches the game through readable wrappers tied to one game build (`MadeForGameVersion`). After a game update:

1. At start, Works checks every game member it looks up (GameNames) and installs its hook groups one by one; a group
   that fails leaves the rest working.
2. If anything didn't fit, the player is told once on the main menu which parts, and that mods using them may not
   work (WorksHealth). Mods can read `WorksApi.Unavailable` and say so themselves.
3. For the fix: `tools/names/Remap.cs` maps the old names to the new build's; update Works, check it on the new game,
   then set `FixVersion.ForGame` (release.sh refuses a release whose game version doesn't match it).

Mods built only on the API need nothing: the same mod DLL keeps working on the updated Works.

## Testing aids

- `tools/smoketest/smoke.sh`: one scripted session with the build and the test mods, 42 checks over the loader's
  rules and the API areas mods use most (release.sh runs it). `tools/smoketest/coop.sh`: a host and a joiner on this
  machine (a test port, never Co-op's own): join, mirrored walking, a fight, a downed player left alone.
  `tools/smoketest/coop-midfight.sh`: joining mid-fight, and loading that mid-fight save without the joiner. `tools/savecheck/check-saves.sh --play`: saves stay
  loadable by the stock game.

- `WORKS_FAIL_GROUP=<group name>` (environment): that hook group fails at start, as after a game update.
- `tools/testmods/HalfBroken`: fails in Load after registering things; nothing it registered may stay.
- `tools/testmods/NeedsNewer`: built against a stand-in for a newer Works; must be refused by name.
